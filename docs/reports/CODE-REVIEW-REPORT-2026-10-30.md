## 1. วัตถุประสงค์และขอบเขต

การตรวจสอบนี้มีวัตถุประสงค์เพื่อประเมินโครงสร้างโปรแกรม ความถูกต้องของตรรกะ การจัดการข้อผิดพลาด การควบคุมสิทธิ์ และความพร้อมสำหรับโครงงานวิชาสัมมนา ตรวจจากซอร์สโค้ด React/TypeScript, service layer, Supabase Edge Function, SQL migrations และ automated tests ที่มีอยู่ในโครงการ

วิธีตรวจประกอบด้วยการอ่านเส้นทางข้อมูลตั้งแต่การเข้าสู่ระบบจนถึงการบันทึกพืชและการดูแล การตรวจเงื่อนไขสิทธิ์ใน migrations และการรัน TypeScript checker, production build และชุดทดสอบเดิม รอบนี้เพิ่มเอกสารรายงานเท่านั้น ไม่ได้เปลี่ยนพฤติกรรมแอปหรือ deploy เพิ่ม

ผลการอ่านโค้ดเป็นการวิเคราะห์แบบ static review ส่วนผลการทดสอบเป็นหลักฐานเฉพาะกรณีที่ชุดทดสอบครอบคลุม ไม่ใช่การรับรองว่าไม่มีข้อผิดพลาดทุกกรณี

## 2. โครงสร้างและการทำงานของระบบ

| ส่วนประกอบ | หน้าที่และไฟล์หลัก |
|---|---|
| ส่วนแสดงผล | React และ TypeScript; `src/App.tsx` ควบคุมหน้าจอและสถานะ ส่วนหน้าต่าง ๆ อยู่ใน `src/components/` |
| ส่วนติดต่อข้อมูล | `src/services/` แยกงาน Auth, พืช, ภารกิจ, ภาพ และประวัติการเติบโตออกจากส่วนแสดงผล |
| การยืนยันตัวตน | Supabase Auth รองรับบัญชีและ Guest; profile เชื่อมกับ Auth user ID และมีขั้นตอนตั้งชื่อฟาร์ม |
| การจัดเก็บข้อมูล | PostgreSQL ผ่าน Supabase และ migrations; Storage เก็บภาพในพื้นที่ของผู้ใช้ |
| การระบุพืช | Edge Function ส่งภาพให้ Pl@ntNet เพื่อระบุชื่อวิทยาศาสตร์ ตัวเลือกใกล้เคียง และค่าความมั่นใจ |
| คำแนะนำการดูแล | Gemini รับชื่อพืชเพื่อให้ชื่อไทยและคำแนะนำ โดยตรวจว่าชื่อวิทยาศาสตร์และค่าความมั่นใจยังคงเดิม |
| กฎของระบบ | Match Score ประเมินจากแสงและตำแหน่งที่ผู้ใช้เลือก ส่วน Aura สะสมจากกิจกรรม โดยมีกฎและการตรวจซ้ำในฐานข้อมูล |

ลำดับการสแกนคือ ผู้ใช้เลือกหรือถ่ายภาพ → ย่อและแปลงเป็น JPEG → อัปโหลด Storage → Edge Function ตรวจเซสชันและเจ้าของภาพ → เรียก Pl@ntNet → เติมข้อมูลจาก Gemini → ตรวจรูปแบบข้อมูล → บันทึกผลสแกน → ให้ผู้ใช้ยืนยันก่อนเพิ่มเข้าสวน

Pl@ntNet confidence เป็นค่าประเมินของบริการระบุพืช ไม่ใช่ผลประเมินความแม่นยำของโครงการจากชุดข้อมูลทดสอบ และ Match Score ไม่ใช่การวัดสุขภาพต้นไม้จากเซนเซอร์

## 3. สิ่งที่ออกแบบได้ดี

1. **แยกความรับผิดชอบของบริการชัดเจน** ภาพส่งให้ Pl@ntNet ส่วน Gemini รับเฉพาะชื่อพืช ช่วยตรวจสอบย้อนกลับได้ว่าผลส่วนใดมาจากบริการใด ไม่ให้คำแนะนำการดูแลเปลี่ยนชนิดหรือคะแนนการระบุพืช
2. **มีการตรวจข้อมูลก่อนนำไปใช้** ใช้ Zod ตรวจโครงสร้างผลลัพธ์ ค่าความมั่นใจ ช่วงอุณหภูมิ และชื่อพืช ก่อนบันทึกหรือแสดงผล จึงไม่เชื่อถือข้อมูลภายนอกโดยตรง
3. **ควบคุมสิทธิ์หลายชั้น** Edge Function ตรวจ token ด้วย `getUser` และตรวจเส้นทางภาพของเจ้าของ ขณะที่ migrations มี RLS และ RPC ตรวจ `auth.uid()` เพื่อลดการอ่านหรือแก้ข้อมูลข้ามบัญชี
4. **เก็บ API key ฝั่งเซิร์ฟเวอร์** โค้ด Edge Function อ่านคีย์จาก environment และ frontend ใช้ publishable key สำหรับเชื่อม Supabase ไม่ใช้ service-role key ในส่วนแสดงผลที่ตรวจ
5. **กฎสำคัญไม่ได้พึ่ง frontend อย่างเดียว** ฐานข้อมูลตรวจความสัมพันธ์ของผลสแกนกับพืช คำนวณคะแนน และใช้การล็อกแถวในงานรางวัล/ดูแล ชุดทดสอบมีกรณีปฏิเสธการแก้คะแนนโดยตรงและการให้รางวัลซ้ำ
6. **จัดการบริการภายนอกขัดข้องได้บางส่วน** มี timeout, retry แบบจำกัดจำนวน และข้อความ fallback เมื่อ Gemini ไม่พร้อม จึงยังใช้ผลระบุชนิดจาก Pl@ntNet ได้
7. **แนวทางดูแลไม่บังคับรดน้ำตามปฏิทินเพียงอย่างเดียว** ระบบใช้ผลตรวจความชื้นประกอบการรดน้ำ และแยกข้อมูลที่ยังไม่ทราบออกจากคำแนะนำที่มีอยู่
8. **มี automated tests ที่ทดสอบกฎจริง** ครอบคลุมสิทธิ์ผู้ใช้ คะแนน รางวัล ภารกิจ กล้อง การแปลชื่อ และการจัดการข้อผิดพลาดจาก API มากกว่าตรวจว่า component เปิดได้เท่านั้น

## 4. ข้อค้นพบจาก Code Review

ระดับ P2 หมายถึงควรแก้เพื่อเพิ่มความถูกต้องหรือความทนทาน ส่วน P3 หมายถึงข้อปรับปรุงด้านประสิทธิภาพและการบำรุงรักษา ระดับนี้ใช้จัดลำดับงานภายในรายงาน ไม่ใช่คะแนนประเมินจากอาจารย์

### 4.1 P2 — ข้อมูลแหล่งคำแนะนำยังระบุ Gemini แม้ใช้ fallback

**หลักฐาน:** `supabase/functions/analyze-plant/index.ts:94` กำหนด `careProvider` เป็น `gemini` เมื่อผลเป็นพืช ขณะที่ `supabase/functions/_shared/gemini-enrichment.ts:10–19` สามารถจับข้อผิดพลาดและคืนข้อความ fallback ได้โดยไม่ส่งสถานะความสำเร็จของ Gemini กลับมา

**ผลกระทบ:** ข้อความบนหน้าจอแจ้งว่า Gemini ไม่พร้อมได้ถูกต้อง แต่ audit metadata ไม่สามารถแยกคำแนะนำจาก Gemini ที่สำเร็จออกจาก fallback จึงอาจทำให้สถิติการใช้งานหรือการอ้างแหล่งข้อมูลในรายงานคลาดเคลื่อน

**ข้อเสนอแนะ:** ให้ enrichment คืนทั้งผลลัพธ์และสถานะ เช่น `careStatus: available | unavailable`, model และรหัสเหตุขัดข้อง แล้วบันทึกแหล่งคำแนะนำตามผลจริง

**สถานะการยืนยัน:** พบจากเส้นทางโค้ดจริงและมี test รองรับเส้นทาง fallback แต่รอบนี้ยังไม่ได้เพิ่ม test ที่ตรวจ audit metadata ในกรณี Gemini ล้มเหลว

### 4.2 P2 — การจำกัดโควตาสแกนยังไม่เป็น atomic operation

**หลักฐาน:** `supabase/functions/analyze-plant/index.ts:48–58` นับจำนวนสแกนย้อนหลังหนึ่งชั่วโมงและตรวจเกณฑ์ 20 ครั้ง ก่อนแยกไป insert แถวใหม่

**ตัวอย่างเงื่อนไข:** เมื่อมี 19 ครั้งและส่งสองคำขอพร้อมกัน ทั้งสองคำขออาจอ่านค่า 19 ก่อนมีคำขอใดบันทึกเพิ่ม จากนั้นทั้งคู่ผ่านและเรียกบริการภายนอก

**ผลกระทบ:** จำนวนสแกนอาจเกินเกณฑ์ที่ตั้งไว้และใช้โควตา API เกินคาด การล็อกการกดใน `App.tsx` ป้องกันได้เฉพาะ frontend instance เดียว ไม่ครอบคลุมหลายแท็บหรือการเรียก endpoint โดยตรง

**ข้อเสนอแนะ:** รวมการตรวจและจองสิทธิ์สแกนไว้ใน transaction/RPC ที่ล็อกตามผู้ใช้ ก่อนเรียก API พร้อมเพิ่ม concurrent-request test

**สถานะการยืนยัน:** เป็น race condition ที่อนุมานจากการแยกคำสั่ง ยังไม่ได้ทำ load test หรือยิงคำขอพร้อมกันบน Supabase จริงในรอบนี้

### 4.3 P2 — ข้อผิดพลาดของภาพหนึ่งรายการอาจกระทบการโหลดสวนทั้งหมด

**หลักฐาน:** `src/services/plants.ts:25–32` และ `src/services/growthLogs.ts:11–15` ใช้ `Promise.all` และรอ signed URL ของแต่ละภาพ โดยไม่มี fallback ต่อรายการ ส่วน `src/App.tsx:65` รอการโหลดทั้งสวน ภารกิจ และ timeline ร่วมกัน

**ผลกระทบ:** หากคำขอสร้าง signed URL รายการหนึ่งคืน error การโหลดทั้งชุดจะ reject และอาจทำให้เข้าสู่หน้าข้อผิดพลาดรวม ทั้งที่ข้อมูลอื่นยังใช้งานได้ ข้อนี้หมายถึง error ตอนขอ URL ไม่ใช่การยืนยันว่าภาพเสียทุกแบบจะทำให้ทั้งสวนล้มเหลว

**ข้อเสนอแนะ:** ใช้ภาพสำรองและจัดการ error ต่อรายการ แยกการโหลด timeline ออกจากข้อมูลหลัก และเพิ่ม test ที่จำลอง signed URL ล้มเหลวเพียงหนึ่งภาพ

**สถานะการยืนยัน:** พบจากลำดับ promise และการส่งต่อ error ยังไม่ได้จำลองไฟล์เสียในฐานข้อมูลจริง

### 4.4 P3 — การโหลดรายการยังไม่มี pagination

**หลักฐาน:** `src/services/plants.ts:21–23` และ `src/services/growthLogs.ts:8` เรียกข้อมูลโดยไม่มี `range` หรือ `limit` และสร้าง signed URL ตามรายการที่ได้รับ ประวัติการดูแลยังถูกกรองแยกต้นไม้ในหน่วยความจำ

**ผลกระทบ:** เมื่อข้อมูลสะสมมากขึ้น จำนวนคำขอภาพและเวลารอเพิ่มขึ้น อีกทั้งผลลัพธ์ขึ้นอยู่กับเพดานจำนวนแถวของ Data API ที่ตั้งไว้ ไม่ควรสรุปว่าได้ข้อมูลครบโดยไม่มีการแบ่งหน้า

**ข้อเสนอแนะ:** แบ่งหน้าประวัติการเติบโต โหลดภาพเมื่อจำเป็น และจัดกลุ่ม care events ตาม plant ID ครั้งเดียวก่อนประกอบรายการ

**สถานะการยืนยัน:** ตรวจพบรูปแบบการโหลดจากโค้ด ยังไม่ได้ benchmark ด้วยข้อมูลจำนวนมาก

### 4.5 P3 — ไฟล์ JavaScript หลักมีขนาดค่อนข้างใหญ่

**หลักฐาน:** Production build รอบนี้สร้าง JavaScript หลักประมาณ 706.61 kB หรือ 187.20 kB เมื่อ gzip และ Vite แจ้งคำเตือน chunk เกิน 500 kB

**ผลกระทบ:** อาจเพิ่มเวลาโหลดครั้งแรกบนโทรศัพท์หรือเครือข่ายช้า แต่คำเตือนนี้ไม่ทำให้ build ล้มเหลว และยังไม่มีผลวัด Core Web Vitals ในรอบนี้

**ข้อเสนอแนะ:** พิจารณา lazy loading หน้าที่ไม่ได้ใช้ทันที เช่น timeline และ profile แล้ววัดผลก่อนและหลังปรับ

## 5. ผลการทดสอบที่ดำเนินการในรอบนี้

| การตรวจสอบ | ผลจริง | ขอบเขตของหลักฐาน |
|---|---|---|
| `npm run lint` | ผ่าน | TypeScript ของ frontend; คำสั่งชื่อ lint แต่ปัจจุบันใช้ `tsc --noEmit` ไม่ใช่ ESLint |
| `npm run build` | ผ่าน มีคำเตือนขนาด bundle | ยืนยันว่าสร้าง production artifact ได้ ไม่ยืนยันทุก user flow |
| `npm test` | ผ่าน 10 tests, ไม่ผ่าน 0 | กฎคะแนน/ดูแล วันที่ กล้อง ชื่อไทย และ migrations |
| `npm run check:edge` | ผ่าน | TypeScript ของ Edge Function |
| `npm run test:edge` | ผ่าน 8 tests, ไม่ผ่าน 0 | การส่งภาพให้ Pl@ntNet การส่งชื่อให้ Gemini การรักษาชนิด/คะแนน และกรณี API ล้มเหลว |

รวม automated tests ที่รันผ่าน 18 test cases โดยบาง test case รวมหลาย assertions ตัวเลขนี้ไม่ใช่เปอร์เซ็นต์ coverage

ข้อจำกัดของชุดทดสอบ:

- Database test ใช้ PGlite ซึ่งเป็น PostgreSQL engine ภายในเครื่อง พร้อม Auth/Storage schemas จำลอง ไม่ใช่การทดสอบ hosted Supabase ครบระบบ
- Edge tests จำลอง HTTP responses จึงไม่ใช้ยืนยันโควตา ความเร็ว ความพร้อม หรือความแม่นยำของ API จริง
- Camera test ใช้ happy-dom และ media mocks จึงไม่ยืนยันกล้องบนอุปกรณ์จริงทุกชนิด
- รอบนี้ไม่ได้ทำ live write, deploy, load test, penetration test หรือการประเมินความแม่นยำด้วยชุดภาพมาตรฐาน
- โค้ด Perenual ยังอยู่และมี test บางส่วนเพื่อความเข้ากันได้ แต่เส้นทางปกติของ local handler ที่ตรวจใช้ Gemini สำหรับข้อมูลดูแล
- การผ่าน tests ไม่เท่ากับไม่มีช่องโหว่ และไม่ได้ยืนยันว่าการตั้งค่า production ตรงกับ migrations ทุกจุด

## 6. งานที่ควรเพิ่มเพื่อประกอบรายงานวิชาสัมมนา

1. จัดทำชุดภาพทดสอบที่มีป้ายกำกับชนิดพืชชัดเจน แยกจากภาพที่ใช้เตรียม demo และบันทึกจำนวนภาพ/จำนวนชนิด
2. วัด top-1 และ top-3 accuracy รวมถึงกรณีภาพไม่ใช่พืช ภาพไม่ชัด และพืชที่ไม่มีข้อมูลดูแล โดยไม่ใช้ confidence ของ API แทน accuracy
3. วัดเวลาตั้งแต่อัปโหลดจนได้ผล และแยกอัตราคำแนะนำ Gemini สำเร็จออกจาก fallback
4. ทดสอบ user flow สมัครบัญชี → ตั้งชื่อฟาร์ม → สแกน → ยืนยัน → เพิ่มสวน → ตรวจดิน → ภารกิจ → บันทึกภาพ → ออกจากระบบ/กลับเข้าใช้ ด้วยสองบัญชีเพื่อยืนยันการแยกข้อมูลจริง
5. ทดสอบอินเทอร์เน็ตหลุด API หมดโควตา ภาพโหลดไม่ได้ และคำขอพร้อมกัน พร้อมบันทึกผลที่คาดหวังเทียบกับผลจริง
6. ระบุสูตรและข้อสมมติ Match Score แยกจาก Aura สะสม ตลอดจนข้อจำกัดว่าระบบไม่ได้วัดแสง อุณหภูมิ หรือสุขภาพพืชจริง
7. ประเมินความเข้าใจและความสะดวกจากผู้ใช้กลุ่มเป้าหมาย พร้อมระบุวิธีคัดเลือกผู้ทดลองและเครื่องมือที่ใช้
8. ระบุ commit และเวอร์ชัน deploy ที่ใช้ทดสอบจริงก่อนส่งรายงาน เพื่อให้ตรวจซ้ำได้ ไม่อ้างชื่อ branch เพียงอย่างเดียว

## 7. ข้อสรุปสำหรับใส่รายงาน

จากการตรวจสอบซอร์สโค้ดและทดสอบอัตโนมัติ พบว่า AuraFarming มีโครงสร้างที่แยกส่วนแสดงผล การติดต่อข้อมูล และกฎของระบบอย่างเหมาะสมกับโครงงานต้นแบบ มีการตรวจสอบข้อมูลจากบริการภายนอกและจำกัดการเข้าถึงข้อมูลตามผู้ใช้ ระบบแยกหน้าที่ Pl@ntNet สำหรับระบุพืชออกจาก Gemini สำหรับชื่อภาษาไทยและคำแนะนำการดูแล และยังแสดงผลการระบุพืชได้เมื่อบริการคำแนะนำขัดข้อง ผลตรวจ TypeScript และ production build ผ่าน รวมถึง automated tests 18 กรณี

อย่างไรก็ตาม ยังควรปรับการบันทึกสถานะคำแนะนำให้ตรงกับแหล่งข้อมูลจริง ป้องกันการแข่งขันของคำขอสแกนพร้อมกัน และแยกข้อผิดพลาดของภาพออกจากการโหลดข้อมูลหลัก ส่วนความพร้อมต่อการใช้งานจริงและคุณภาพการระบุพืชยังต้องประเมินด้วยระบบที่ deploy อุปกรณ์จริง และชุดภาพทดสอบที่กำหนดเกณฑ์ชัดเจน ผลการตรวจครั้งนี้จึงสนับสนุนว่าระบบมีพื้นฐานสำหรับ MVP แต่ยังไม่เพียงพอที่จะรับรองความถูกต้องหรือความพร้อมใช้งานทุกสถานการณ์
